Strengths

The code is clean, well-organized, and the trail-detection state machine and XP math are genuinely well-built. The problems are concentrated in the authorization model — the Appwrite backend treats the client as trusted, and one misconfiguration is a directly exploitable privilege-escalation bug.

Critical

Critical Privilege escalation: any user can self-approve and self-promote to admin

scripts/setup-backend-collections.js:163-177 · stores/useProfileStore.ts · app/(auth)/register.tsx

The profiles collection is configured with documentSecurity: false and a collection-level update("users") permission:

permissions.add('create("users")')
permissions.add('read("any")')
permissions.add('update("users")')      // ← every logged-in user can update…
permissions.add('update("team:admins")')
// ...
documentSecurity: false,                // …ANY document, ANY field

Why it's dangerous

Appwrite has no field-level permissions. update means "update any attribute of any document in the collection." Because approved and isAdmin live on the same profile document, any registered user — even one that hasn't been approved — can issue a single SDK call to:

  • set their own approved: true → bypass the approval gate in app/(app)/_layout.tsx:23
  • set their own isAdmin: true → unlock the admin panel
  • rewrite any other user's xp, level, username, or approval status

The client already performs exactly these writes (databases.updateDocument(DB_ID, PROFILES_ID, …) in useProfileStore.ts:51 and admin/index.tsx:21). An attacker simply calls the same function with a different document ID and payload.

Recommended fix

  • Set profiles to documentSecurity: true; grant each profile per-document update(Role.user(id)) for the owner.
  • Move approved / isAdmin writes into a server-side Appwrite Function (API-key scoped), never reachable by the users role.
  • Restrict approval mutations to team:admins + the server function only.

Critical XP and leaderboards are entirely client-trusted

stores/useProfileStore.ts:34-59 · stores/useRunStore.ts:93-100

Even setting aside the permission bug, addPendingXp / claimPendingXp write xp and level directly from the client, and run metrics (totalTime, maxAirtime, maxGForce, …) are simply whatever the client posts:

await databases.updateDocument(DB_ID, PROFILES_ID, profile.$id, {
  xp: newXp, level: newLevel, pendingXp: 0,   // client decides its own XP
})

Why it's dangerous

Any user can fabricate a run with a 50 G impact and a 0-second time, or write an arbitrary XP value, and top every leaderboard. The logic in lib/xp.ts looks authoritative but runs only on the device, so it provides no integrity guarantee.

Recommended fix

  • If leaderboard integrity matters: compute XP and validate run metrics server-side (Appwrite Function reusing lib/xp.ts), and make xp / level / run metrics non-writable by the client.
  • If it doesn't (friends-only app): that's a legitimate choice — but document it, because the current code reads as if it's enforcing rules it can't enforce.

High The "fire" / like feature is broken for everyone but the post author

stores/useFeedStore.ts:31,46 · scripts/setup-backend-collections.js:266

Clip posts are created with documentSecurity: true and write granted only to the author (Permission.write(Role.user(data.userId))), and the clip_posts collection itself only has create("users") + read("any"). But toggleFire updates fireCount / firedBy on another user's post:

await databases.updateDocument(DB_ID, CLIP_POSTS_ID, postId, {
  fireCount: newCount, firedBy: newFiredBy,   // rejected unless you own the post
})

Why it's a problem

  • Functional: the write is denied for everyone except the post owner, so likes don't work for their intended purpose.
  • Race condition: toggleFire reads fireCount, modifies it locally, and writes it back. Two simultaneous fires clobber each other — the count drifts.

Recommended fix

Handle fires in a server-side Function (lets non-owners increment safely) or use an atomic increment if your Appwrite version supports incrementDocumentAttribute. Store the per-user fire relationship in a separate collection rather than mutating the post's array.

High Admin route is not guarded — only the button is hidden

app/(app)/admin/index.tsx · app/(app)/(tabs)/profile.tsx:320 · app/(app)/_layout.tsx

The "Admin" entry point is conditionally rendered behind isAdmin in the profile UI, but the route file app/(app)/admin/index.tsx has no isAdmin redirect. The only gate is the group layout's session + approved check, so a non-admin can deep-link straight to the admin screen.

Why it's a problem

Defense in depth is missing on the client, and — combined with the Critical permission bug above — the approve action a non-admin triggers there actually succeeds server-side.

Recommended fix

Add an isAdmin redirect guard at the route, and (more importantly) enforce admin-only mutations server-side. UI hiding is not a security control.

Low Auth bypass flags can silently ship an open app

app/(app)/_layout.tsx:7,20

SKIP_AUTH_FOR_SENSOR_TEST and IS_DEMO render the whole app with no auth. IS_DEMO is !process.env.EXPO_PUBLIC_APPWRITE_ENDPOINT — it triggers whenever that env var is unset. Make sure production builds always set the endpoint, or a misconfigured build ships with authentication disabled.

Low Leaderboard queries fetch a fixed 200-row window then sort client-side

stores/useRunStore.ts:188-201, 122-138, 157-177

getLeaderboard, getWeeklyRanking, and getPersonalBests pull Query.limit(200) and then dedupe / compute "best per user" in JS. Fine at small scale, but once the runs collection exceeds 200 rows in the window, entries are silently dropped and the "best" can be wrong. Plan to paginate or push aggregation server-side as data grows.

Low Pervasive as unknown as T casts defeat type safety

stores/useAuthStore.ts:26-27 and most store files

Appwrite returns Models.Document; the code casts straight to domain types (as unknown as Run, as boolean) everywhere. A schema drift would surface as a runtime undefined rather than a compile error. Consider a small typed mapper layer per collection so the boundary is validated once.

Bottom line: architecturally solid and pleasant to read, but the Appwrite permission model trusts the client. The profiles documentSecurity: false + update("users") combination (Critical #1) is a real, exploitable auth bypass and should be fixed before any real users touch the app. The fire feature (High #1) is currently non-functional for its intended use.
